# Internationalization

The app uses i18next 26 and react-i18next 17 behind an application-owned facade. See [dependency boundaries](AGENTS.md#shared-internationalization-boundary) and [naming conventions](../conventions/AGENTS.md#identifiers). Only bootstrap assembles concrete storage, device detection and translation services. Instances are created per mounted application, never at module scope.

## Consumers

Import `useAppTranslation`, `useAppLocale`, `useAppFormatting` and `AppTranslatedText` from `@/shared/i18n`. For example, `useAppTranslation("common").t("editScreen", { file: "src/app/index.tsx" })`. Namespace and key autocomplete and required interpolation values derive from generated pure message literals. No i18next types are exposed. Changing vendor still requires migrating catalog syntax and the adapter, but preserves consumer contracts.

`AppTranslatedText` takes a fully qualified `message`, typed `values` and a named `components` map. Supply React Native `Text`-compatible elements for inline content. Components and links are controlled by code. It subscribes to language changes through the shared context; Trans alone does not subscribe.

## Locale and lifecycle

Supported locales are `en` and `pt-BR`, with `en` as the default and fallback. Saved explicit preference wins over the first supported device locale; exact matches precede language-family matching. Portuguese variants resolve to pt-BR and English variants to en. The `system` preference follows the device, including after returning to foreground. `setPreference` persists before publishing and rejects storage failures without changing the visible preference. Operations are serialized to prevent overlapping changes. Invalid stored values behave like system preference; read failures are reported and startup continues. Preference is non-sensitive and uses the existing LocalStorage/MMKV adapter under `app-preferences`, key `i18n.locale-preference`.

Startup happens in an effect with cancellation cleanup. Until ready, the root renders an empty shell. On failure, a bilingual retry control is available because catalogs may not be usable yet. Web server rendering therefore produces a deterministic empty shell, with client-side localization after mount; this implementation does not provide localized SSR or SEO content. No request-shared mutable translation instance is used. Native initial rendering waits for local resources only; no network or remote backend is involved.

## Catalog maintenance

JSON catalogs live in infrastructure, grouped by locale and namespace. English (`en`) is the reference catalog for generated types and catalog validation. The pt-BR directory uses kebab-case (`pt-br`), while locale tags use BCP 47 (`pt-BR`). Use semantic keys and complete phrases, not concatenated fragments. Keep `common` small; create business namespaces only for real consumers. Plural suffixes follow each locale's Intl.PluralRules categories, so suffix sets can differ between locales.

After catalog edits run `pnpm i18n:types`; commit the generated `shared/i18n/app-messages.ts`. `pnpm i18n:check` detects stale output. The generator preserves literal values so required interpolation variables remain typed; `count` is numeric. Run catalog tests as well: type generation does not validate translation quality. Do not manually edit generated types.

All catalogs are bundled for reliable offline startup. Namespace separation does not itself reduce the native binary. Introduce remote loading only after measurement, with explicit cache/version/fallback behavior. To add a locale update the pure locale union, adapter registry/resources, JSON catalogs, catalog tests and expo-localization supportedLocales. Run generation and all checks. Native supportedLocales changes require a new binary. RTL is disabled initially; RTL locales require deliberate layout, navigation and native configuration work.

## Formatting and native support

`useAppFormatting` caches Intl formatters for the active locale. Currency requires the actual ISO currency code and never converts money. Percent accepts ratios (`0.15` means 15%). Pass a timeZone when business semantics require it; otherwise the runtime's local zone applies. Handle calendar-only dates without accidental UTC shifts. The DateAdapter contract retains parsing/arithmetic and its existing technical formats.

The adapter loads intl-pluralrules before initializing i18next for Hermes compatibility. Verify Intl.DateTimeFormat and Intl.NumberFormat in iOS and Android development builds. expo-localization is configured through app.json and CNG; do not edit generated native projects. Adding its native module or changing the plugin requires rebuilding. Unit tests cannot establish actual OS language behavior, disk persistence or runtime locale data availability.

## Verification

Use isolated real translator instances with fake storage/device locales. Native component tests exercise reactive translation, rich text and formatting, while Router tests cover the route and localized title. Type assertions ensure invalid keys and missing variables fail compilation. Catalog checks compare logical messages, placeholders, markup and locale-specific plural requirements. Run `pnpm i18n:check`, `pnpm lint`, `pnpm check`, `pnpm typecheck` and `pnpm test`. Device verification should include relaunch, system-language changes, explicit overrides and returning to system mode.
